## Loopback benchmark (`make bench`)

Simulated root, com and example.com servers on loopback UDP; 300 distinct names, a fresh cache per
name; then 500 HTTP GETs each way.

| Measurement | Runs | Median | p95 |
|---|---|---|---|
| DNS cold resolution (3 UDP queries: root, com, example.com) | 300 | 1,982 us | 4,133 us |
| DNS same name again (served from cache, 0 queries) | 300 | 27 us | 85 us |
| HTTP GET on one keep-alive connection | 500 | 347 us | 574 us |
| HTTP GET with a new TCP connection each time | 500 | 676 us | 1,075 us |

## Analyze and Improve

- **Defect found by the benchmark:** the first `UdpTransport` opened a `Selector` per query to wait
  with a timeout. Cold resolution took a median of 14,223 us and a p95 of 142,478 us (log kept as
  `.tmp/bench-baseline-selector.log`). Root cause: on Windows, opening a `Selector` sets up an internal
  wakeup socket pair, which costs milliseconds and occasionally much more.
- **Improvement:** wait with a timed blocking receive on the channel's socket instead. Same benchmark:
  median 1,982 us, p95 4,133 us (about 7x faster median, 34x lower p95). All 92 Java tests passed
  unchanged.
- **Keep-alive:** a new TCP connection per request roughly doubles loopback latency (676 vs 347 us);
  over a real network each new connection also costs a round trip for the handshake.
- **Flaky test found and fixed:** `DnsServer` bound UDP on a free port and then TCP on the same number;
  once, another program already held that TCP port. The server now retries with a new port.

`live-dns` job that resolves example.com from the root and prints a `::notice`, and `make audit`.
